# 模块 5：通信器缩容与故障恢复

## 做了什么

实跑部分只做 ⑤-2：两卡建父通信器，rank1 跑完一次 all-reduce 后直接退出，模拟故障，rank0 调 `ncclCommShrink` 把坏掉的 rank 踢出去，在新通信器上继续 all-reduce。其余两项 ⑤-1 作业级重调度与 ⑤-3 NVCRE 认证没有多节点环境，写成设计文档放进 `results/paper/`。

## 代码与编译

源码在 [shrink_demo.c](../scripts/shrink_demo.c)。核心调用：

```c
int exclude[1] = {1};
ncclComm_t shrunk = NULL;
r = ncclCommShrink(parent, exclude, 1, &shrunk, NULL, NCCL_SHRINK_ABORT);
```

编译需要带 MPI，示例里有 `MPI_Init` 与 `MPI_Bcast`：

```bash
mpicc shrink_demo.c -I/usr/local/cuda/include -L/usr/local/cuda/lib64 -lcudart -lnccl -o shrink_demo
```

## 运行原文

```text
rank 0: parent comm init rc=0 nranks=2
rank 1: parent comm init rc=0 nranks=2
rank 0: parent allreduce rc=0 result[0]=3.0 (expect 3.0)
rank 1: parent allreduce rc=0 result[0]=3.0 (expect 3.0)
rank 1: simulating failure, exiting without destroying parent comm
rank 0: ncclCommShrink rc=0 (no error)
rank 0: shrunk comm size=1 myrank=0
rank 0: shrunk allreduce rc=0 result[0]=1.0 (only remaining rank, expect 1.0)
rank 0: SUCCESS - shrink done without re-generating uniqueId
RC=0
```

前三行确认父通信器可用：两卡各取 rank+1，all-reduce 求和为 3。第五行是故障注入，rank1 在父通信器仍然存在的情况下退出，没有调 `ncclCommDestroy`。

第六行是关键：`ncclCommShrink` 返回 0。第七行 `size=1 myrank=0` 说明新通信器里只剩 rank0。第八行在新通信器上完成 all-reduce，结果 1.0。

## 单 rank all-reduce 的含义

size=1 的 all-reduce 只有自己一个加数，结果等于输入。NCCL 在只有单 rank 时把操作退化成本地拷贝，不产生跨卡通信。这一行不能当作"缩容后通信仍然正常"的证据。

缩容的价值在别处：rank0 拿到一个可用的新通信器，进程没有重启，uniqueId 没有重新生成，其他 rank 不需要重新加入。这种机制适用于部分 rank 掉线、剩余节点继续训练的容错场景。

## 结论

`ncclCommShrink` 在 NCCL 2.32.6 上可用：踢掉故障 rank 后，剩余 rank 不重新分配 uniqueId、不重启进程，直接在新通信器上继续工作。这是 NCCL 从"建通信器"到"动态调整通信器"的能力扩展。

## 说明了 NCCL 的什么

1. 通信器是带状态的实体，rank 集合写死在创建时刻。传统做法是任一 rank 掉线就整体重建；`ncclCommShrink` 提供了保留剩余成员的路径。
2. `NCCL_SHRINK_ABORT` 决定父通信器上未完成操作的处理方式：直接中止，不等对方响应。没有这个标志，调用会卡在等一个已经退出的 rank。
3. 缩容解决的是通信器层面的成员变更。作业级恢复还要配合 checkpoint 与重调度，两件事分开设计（⑤-1）。
