# 模块 3：官方示例 01–07

## 做了什么

在 `/root/nccl-src/docs/examples` 下编译并运行了 01 到 07 七个主题的 C 版本示例，每个示例的日志落在 `logs/m3_0X.log`，编译日志落在 `logs/m3_0X_build.log`。

统一用 `make` 编译，`PATH` 里加 `/usr/local/cuda/bin`。二进制用 sm_80 编译，与 A100 的算力等级一致。

## 各示例的结果与原文

### 01_communicators：三种进程组织方式

```text
Using ncclCommInitAll() to create all communicators simultaneously
All 2 NCCL communicators initialized successfully
  Communicator 0: Rank 0/2 on CUDA device 0
  Communicator 1: Rank 1/2 on CUDA device 1
```

单进程多卡用 `ncclCommInitAll` 一次建好两个通信器。pthread 版本里两个线程各建一个通信器，MPI 版本里由 rank0 生成 uniqueId 广播给 rank1：

```text
Rank 0 generated NCCL unique ID for all processes
INFO: Rank 1 received NCCL unique ID
  Rank 1 created NCCL communicator
  MPI rank 1 → NCCL rank 1/2 on GPU device 1
```

三个子项都退出码 0。

这里踩到一个编译问题。`01_communicators/Makefile` 的默认目标只编前两个子项，MPI 那个需要 `MPI=1`：

```text
mpirun was unable to launch the specified application as it could not access
or execute an executable:

Executable: ./03_one_device_per_process_mpi/c/one_device_per_process_mpi
```

退出码 132。补 `make MPI=1` 后重跑通过。退出码 132 是 `mpirun` 启动进程失败，检查二进制是否存在比查代码快。

### 02_point_to_point：ring 收发

```text
Ring communication completed successfully
  GPU 0 received data from GPU 1: CORRECT
```

两个 rank 沿环形互发，`ncclSend` 与 `ncclRecv` 成对提交。这是流水线并行里相邻段通信的最小形态。

### 03_collectives：最小 all-reduce

```text
  Device 0 correctly received sum: 1
  Device 1 correctly received sum: 1
```

两卡各持一个值（0 和 1），求和后两边都拿到 1。`ncclAllReduce` 的七个参数依次是发送缓冲、接收缓冲、元素个数、数据类型、归约算子、通信器、CUDA 流。

### 04_user_buffer_registration：显存预注册

```text
Starting AllReduce with 1048576 elements (4 MB)
AllReduce completed successfully
Results verified correctly
```

用 `ncclMemAlloc` 分配显存、`ncclCommRegister` 注册给通信器，结束再注销。注册后 NCCL 直接读写这块显存，省掉内部中转拷贝。推理场景的权重与 KV cache 都是预分配的，走的就是这条路径。

### 05_symmetric_memory：对称内存

```text
AllGather completed successfully
Verification - Segment 0: Expected: 0.0, Got: 0.0
Verification - Segment 1: Expected: 1.0, Got: 1.0
All resources cleaned up successfully
```

两个 rank 的 buffer 地址与布局完全对称，通信时按对端偏移直接寻址。`allreduce_sm` 与 `allgather_ce` 两个子项都通过。第二项还演示了借 copy engine 做 allgather。

这个示例要求 NCCL ≥ 2.27，本机系统库是 2.32.6，满足条件。

### 06_device_api：kernel 内发起通信

```text
  Rank 1 created device communicator with 16 LSA barriers
  Rank 0 created device communicator with 16 LSA barriers
AllReduce completed. Result verification: PASSED
```

`ncclDevCommCreate` 把通信器转成设备侧可用的 devComm，kernel 内用 `ncclGetLsaPointer` 取对端显存地址、`ncclTeamTagLsa` 圈定团队。每卡建了 16 个 LSA barrier。通信的发起从 CPU 侧移到 kernel 内，省掉 kernel 外发起的开销。

只跑了 LSA 子项。`02_alltoall_gin` 与 `03_alltoall_hybrid` 需要 GIN 的 RDMA 网络，单机没有；两个 CFT 子项需要 multimem，Ampere 不支持。

### 07_kernel_fusion：RMSNorm 与 all-reduce 融合

```text
Configuration:
  - Total ranks:      2
  - Sequence length:  128 tokens
  - Hidden size:      1024
  - Tokens per GPU:   64
SUCCESS: Example completed successfully!
```

归一化计算与跨卡归约放进同一个 kernel，对应推理每层 forward 的真实模式。其余子项依赖 multimem 或 GIN，没有编译。

## 结论

七个主题全部通过，覆盖了 NCCL 从通信器创建、点对点、集合通信、显存注册、对称内存、设备侧 API 到 kernel 融合的完整 API 层次。唯一失败点是 01 的 MPI 子项没有编译，与 NCCL 本身无关。

## 说明了 NCCL 的什么

1. API 在按使用场景分层。最上层是集合通信，中间是显存注册与对称内存，底层是设备侧 API。层次越往下，CPU 侧开销越少，对 kernel 结构的侵入越大。
2. uniqueId 是建立通信器的握手凭证，广播方式随进程模型变化：单进程内直接传递，pthread 用共享内存，MPI 用集合通信广播。三种方式证书交换的路径不同，后续通信行为完全一致。
3. 对称内存与设备侧 API 是近两年新增的能力，版本门槛明显。05 要 2.27，06 与 07 需要更完整的设备 API。多机与新硬件特性还要额外条件，比如 multimem 要 Hopper 及以上，GIN 要 RDMA 网络。选型时先确认版本与硬件，再决定用哪一层。
