# 模块 4：all-reduce 基线与参数调优

## 做了什么

用 nccl-tests 2.21.1 编译 `all_reduce_perf`，先跑一遍 8B 到 8GB 的全量基线，再在 1MB 与 1GB 两个固定尺寸上比较 `NCCL_ALGO` 与 `NCCL_PROTO` 的六种组合。全部单节点双卡。

```bash
./build/all_reduce_perf -b 8 -e 8G -f 2 -g 2
```

四个参数：`-b 8` 起始 8 字节，`-e 8G` 封顶 8GiB，`-f 2` 每档乘 2，`-g 2` 用两张卡、每卡一个 rank。8 到 8GiB 共 31 档，每档预热 1 次、正式 20 次取均值。

## 基线原文

开头与结尾：

```text
# nccl-tests version 2.21.1 (afd59ab) nccl-headers=23206 nccl-library=23206
# nThread 1 nGpus 2 minBytes 8 maxBytes 8589934592 step: 2(factor) warmup iters: 1 iters: 20
#
# Out of bounds values : 0 OK
# Avg bus bandwidth    : 6.85626
```

`nccl-library=23206` 表示链接的是系统 NCCL 2.32.6。这一条要和模块 1 的 2.30.7 区分开：vLLM 走 torch 自带的库，`nccl-tests` 走系统库，两者数字不可直接横向比较。

小、中、大三档各摘两行：

```text
           8             2     float     sum      -1    21.86    0.00    0.00       0
        1024           256     float     sum      -1    18.30    0.06    0.06       0
       32768          8192     float     sum      -1    19.99    1.64    1.64       0
     1048576        262144     float     sum      -1   110.50    9.49    9.49       0
   268435456      67108864     float     sum      -1  18566.3   14.46   14.46       0
  8589934592    2147483648     float     sum      -1   578276   14.85   14.85       0
```

列含义：消息字节数、元素个数、数据类型、归约算子、root、耗时（微秒）、algbw（GB/s）、busbw（GB/s）、错误数、第二组 in-place 数据。两个带宽列在 n=2 时数值相等，因为 all-reduce 的换算系数是 `2(n−1)/n`，n=2 时为 1。

全表见 [m4_baseline_table.md](../results/test/m4_baseline_table.md)。

## 分段的读法

小消息段 8B 到 4KB，耗时稳定在 18 到 22 微秒，busbw 显示 0.00 或 0.01。这一段的耗时由延迟决定，8 字节乘 20 次迭代也传不了多少数据，带宽字段没有参考价值。

中段 32KB 到 16MB，busbw 从 1.64 爬到 12.7。消息变大后传输时间开始超过固定延迟，曲线向上。

大消息段 256MB 到 8GB，busbw 稳定在 14.5 到 14.85。这一段由链路带宽决定，8GB 时的 14.85 就是本机 all-reduce 链路的实测上限。

平均 6.86 被小消息档拉低，不代表平台能力，写结论时用大消息段的 14.85。

## 拓扑对数值的影响

本机 `nvidia-smi topo -m` 显示 GPU0 与 GPU1 之间是 PHB，两卡挂在同一个 PCIe 主机桥下，没有 NVLink。14.8GB/s 这个平台值对应 PCIe 路径。

requirement 按 A800 NVLink 写的预期是 400GB/s 量级（双向口径）的六到八成。同一份命令在 NVLink 机器上能得到一百多到两百多 GB/s。数值差一个量级来自硬件，基线表的标注按实际拓扑写成"单节点双卡、PCIe（PHB）拓扑下实跑"。

## 调优六组

| 尺寸 | 配置 | busbw（GB/s） | 相对默认 |
|---|---|---:|---:|
| 1MB | 默认 | 9.49 | — |
| 1MB | `NCCL_ALGO=Tree` | 5.38 | −43.3% |
| 1MB | `NCCL_PROTO=LL` | 3.32 | −65.0% |
| 1GB | 默认 | 14.69 | — |
| 1GB | `NCCL_PROTO=Simple` | 14.61 | −0.5% |
| 1GB | `NCCL_ALGO=Tree` | 14.31 | −2.6% |

六组 `#wrong` 全为 0，即结果校验通过。

1MB 档强制指定都变慢。默认组 9.49，Tree 降到 5.38，LL 降到 3.32。LL 协议在 NVLink 上靠低延迟链路段落取胜，本机的 PCIe 路径上这个优势不存在，额外的握手与同步反而变成开销。Tree 算法在 2 个 rank 时退化成链式，也占不到便宜。

1GB 档三组几乎重合。带宽已经顶到 PCIe 上限，换算法换协议都挤不出空间。差异 2.6% 以内，落在测量噪声范围。

## 结论

1. 本机的 all-reduce 平台值是 14.85GB/s，瓶颈在 PCIe 链路，与算法选择无关。
2. 双卡规模下 NCCL 的自动选择优于强制指定。调优收益要在规模（多节点）或特殊消息尺寸（极小消息）上才出现。
3. 小消息的固定开销约 18 微秒。推理每层两次 all-reduce，这个开销乘以层数就是 TP 的通信成本下限。
4. 三个参数组合没有一组超过默认配置。把"LL 小消息更优"当通用结论使用会在 PCIe 机器上得到反向结果。

## 说明了 NCCL 的什么

1. busbw 是归一化后的链路带宽，考虑 collective 的数据放大倍数，才能跨 collective 类型比较。algbw 是原始吞吐，两者在 all-reduce、n=2 时数值相同，换 collective 或换卡数就会分开。
2. NCCL 在通信器建立后按消息大小与拓扑选算法与协议。这个选择在运行时逐消息进行，所以强制指定只适合做对照实验，不适合长期配置。
3. 带宽上限由拓扑决定，软件调优只能逼近它。先量出平台值，再判断剩余优化空间，是排查通信性能的固定顺序。
